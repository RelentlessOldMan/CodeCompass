CodeCompass

Fast, fully-local code search & navigation for large codebases — built to cut the tokens an AI coding agent spends finding code.

In one line: CodeCompass indexes your repo on your machine and gives Claude Code (or your terminal) precise file:line:col answers — text search, go-to-definition, and find-references — instead of the agent grepping blindly and reading whole files. Nothing leaves your machine. No GPU. No cloud.

What it is & why

An AI coding agent's default moves — grep for a string, then read entire files to understand a match — are cheap on a small repo and ruinously token-hungry on a big one. CodeCompass returns just the lines that matter, so the agent spends its context on thinking, not on scrolling files it didn't need.

It's three complementary layers, cheapest first:

  • Lexical — a trigram index for instant literal/substring search across the whole repo.
  • Symbolic — tree-sitter parses every file into symbols (classes, methods, functions…) for go-to-definition.
  • Semantic — real find-references for C# (Roslyn) and C/C++ (clang): it resolves the actual symbol and ignores matches in comments and strings, which a text search can't.

Minimal token footprint

A pain point with some in-house tools is that they register a pile of MCP tools/skills that eat context every session. CodeCompass exposes exactly 5 tools with terse descriptions — that's the entire standing per-session cost.

Install

Requires the .NET 8 SDK to build; the produced binaries are self-contained (no .NET needed to run them). Windows x64.

Windows on ARM (Snapdragon): no separate ARM build is needed — the x64 binaries run on Windows 11 on ARM through its built-in x64 emulation (the whole process, native dependencies included, runs emulated). Searches stay effectively instant; only the first index build runs somewhat slower than on native x64.

pwsh ./build-plugin.ps1      # publishes self-contained binaries into plugin/bin

Then load it into Claude Code:

claude --plugin-dir "<path>/plugin"     # one session
/plugin add "<path>/plugin"             # persistent (run inside Claude Code)

In a session, run /mcp to confirm the codecompass server is connected.

Using it from Claude Code

Once installed you don't do anything special — just ask Claude to work in your repo. It gets the CodeCompass tools, and a hook redirects Grep/Glob to CodeCompass so the agent uses the index instead of scanning files. (Set CODECOMPASS_ENFORCE=0 to allow grep again.) The index builds automatically on first use for normal-sized workspaces and stays fresh as files change.

Large repos: a very large workspace isn't auto-indexed inside a tool call (that could stall). CodeCompass tells you to build it once from a terminal — see below — then it serves and keeps it fresh.

Using it from the command line

codecompass index   <path>            build the index (shows progress + ETA)
codecompass update  <path>            incremental reindex of changes
codecompass watch   <path>            auto-reindex on file changes
codecompass search  <path> <query>     literal text search  -> file:line:col
codecompass def     <path> <name>      go-to-definition
codecompass refs    <path> <name>      references (semantic C#/C++, lexical elsewhere)
codecompass symbols <path> <substr>    symbol-name search
codecompass survey  <path>            report what the size caps skip + suggest config
codecompass logs                      show the log folder and files
codecompass version                   print the build version (e.g. 1.0.52+a76d3245)

Tuning for huge or generated trees

Indexing is robust on ordinary source at scale. The one hazard is dense machine-generated files (e.g. multi-MB register-map headers that are millions of #define lines): tree-sitter's parse cost is roughly O(n²) on such content. That is bounded by default — symbol extraction is skipped above CODECOMPASS_MAX_SYMBOL_MB (1 MB), and those files are still fully trigram-indexed, so text search stays complete. In practice it never touches hand-written code: across the test corpora, every source file over 1 MB was machine-generated. Files skipped for a cap are counted and logged, so the coverage gap is visible rather than silent.

Environment variableEffect
CODECOMPASS_MAX_SYMBOL_MBSkip tree-sitter symbol extraction above this size (default 1). Raise it for large valid generated code whose symbols you want.
CODECOMPASS_MAX_FILE_MBPer-file size cap for indexing entirely (default 5).
CODECOMPASS_IGNOREComma/semicolon-separated directory names to exclude (e.g. generated,vendor).
CODECOMPASS_MAX_AUTO_MBWorkspaces larger than this (default 100) are left for a one-time CLI build instead of auto-indexing in a tool call.
CODECOMPASS_THREADS / CODECOMPASS_SEGMENT_MBIndexing parallelism / per-worker build-memory budget.
CODECOMPASS_READ_BUDGET_MBCap on total file bytes held in memory at once during a parallel build (default scales to RAM: ~1/16th of available, clamped 256 MB–4 GB). Stops N cores from each loading a multi-GB file at once when MAX_FILE_MB is large; an over-budget file reads solo.
CODECOMPASS_ENFORCE=0Allow the agent to use Grep/Glob again (the hook redirects them to CodeCompass by default).

Every knob also lives in an optional .codecompass.json at the repo root, so settings travel with the repo (precedence: env → config file → default). Fields: maxSymbolMb, maxFileMb, maxAutoMb, ignore (directory names), threads, segmentMb, compactSegments, stallWarnSec, readBudgetMb. Run codecompass survey <path> first: it reports what the caps skip, names the largest files, and suggests a change — with the O(n² ) caveat. It never auto-raises a cap; file size isn't a reliable signal of parse safety, so that call is left to the repo owner.

Performance

Measured on: Intel Core i7-8700 (6 cores / 12 threads, ~2018), 32 GB RAM, Windows 11 Pro, .NET 8. A modern many-core laptop (e.g. 32 threads) will be substantially faster to build. These figures were recorded before the EcoQoS / E-core throttling opt-out, so build throughput is conservative here — expect higher on hybrid CPUs (up to ~2× where the OS was previously parking the process on efficiency cores).

How to read this: Build is the first full index (parallel across cores; faster on more cores). Query is search latency — typically ~1 ms. Correct = trigram search verified against a brute-force scan on the real files.

At ~25 MB/s a first index of a dozens-of-GB repo is on the order of minutes-to-tens-of-minutes (less on a many-core machine), and searching it afterward uses only a few hundred MB of RAM — comfortably within a 16 GB laptop.

Scale check (10 GB / ~1.1 million files): an aggregated 10.4 GB corpus indexed in 7m48s (22 MB/s) on the machine above, using 792 MB heap / 2.2 GB peak working set during a full build-plus-edit cycle. Queries stayed ~1 ms (p95 7.9 ms). Memory stays bounded because the trigram and symbol indexes — and the change-detection ledger — are all memory-mapped on disk, not loaded into RAM, so searching a repo this size uses only a few hundred MB and editing it keeps just the changed files in memory. First-time build memory is tunable via CODECOMPASS_SEGMENT_MB / CODECOMPASS_THREADS.

Logs & troubleshooting

CodeCompass keeps a self-limiting log on disk so problems can be diagnosed after the fact without watching it live. Everything lives in one folder — run codecompass logs to print the location and the current files:

%LOCALAPPDATA%\CodeCompass\logs\
  codecompass.log              common log: startup + every warning/error, all repos
  repo-<name>-<key>.log         per-repo log: full detail (builds, incremental reindex, skips)

Each file is size-capped and rotated (default 5 MB × 4 files kept), so the logs can never grow unbounded — at most ~20 MB per file family. Warnings and errors from a repo are mirrored up into the common log, so that one file is the first place to look when something's off.

SettingEffect
CODECOMPASS_LOG_LEVELoff / error / warn / info (default) / debug
CODECOMPASS_LOG=0disable logging entirely
CODECOMPASS_LOG_DIRwrite logs somewhere other than the default folder
CODECOMPASS_LOG_MAX_MBrotate each file at this size (default 5)
CODECOMPASS_LOG_KEEPhow many rotated files to keep (default 3)

Logging never throws and never blocks indexing or search — if the log can't be written it's silently skipped. Set CODECOMPASS_LOG_LEVEL=debug to record per-file skips and detailed build stats when chasing a specific issue.
