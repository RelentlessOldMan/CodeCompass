CodeCompass

Fast, fully-local code search & navigation for large codebases — built to cut the tokens an AI coding agent spends finding code.

In one line: CodeCompass indexes your repo on your machine and gives Claude Code (or your terminal) precise file:line:col answers — text search, go-to-definition, and find-references — instead of the agent grepping blindly and reading whole files. Nothing leaves your machine. No GPU. No cloud.

What it is & why

An AI coding agent's default moves — grep for a string, then read entire files to understand a match — are cheap on a small repo and ruinously token-hungry on a big one. CodeCompass returns just the lines that matter, so the agent spends its context on thinking, not on scrolling files it didn't need.

It's three complementary layers, cheapest first:

  • Lexical — a trigram index for instant literal/substring search across the whole repo.
  • Symbolic — tree-sitter parses every file into symbols (classes, methods, functions…) for go-to-definition.
  • Semantic — real find-references for C# (Roslyn): it resolves the actual symbol. Every other language, C and C++ included, gets a fast name search for references: whole-word uses in code, never the definition itself, and for C and C++ never inside a comment or string.

Minimal token footprint

A pain point with some in-house tools is that they register a pile of MCP tools/skills that eat context every session. CodeCompass exposes a deliberately small 7 tools with terse descriptions — that's the entire standing per-session cost.

Install

Requires the .NET 8 SDK to build; the produced binaries are self-contained (no .NET needed to run them). Windows x64.

Windows on ARM (Snapdragon): no separate ARM build is needed — the x64 binaries run on Windows 11 on ARM through its built-in x64 emulation (the whole process, native dependencies included, runs emulated). Searches stay effectively instant; only the first index build runs somewhat slower than on native x64.

pwsh ./build-plugin.ps1      # publishes self-contained binaries into plugin/bin

Then load it into Claude Code (there is no /plugin add command):

claude --plugin-dir "<path>/plugin"                    # one session
/plugin marketplace add "<path>/plugin"                # persistent: register the folder…
/plugin install codecompass@codecompass                # …then install (run inside Claude Code)

The prebuilt release zip unzips to a folder you point at the same way (it ships a self-marketplace). In a session, run /mcp to confirm the codecompass server is connected.

Using it from Claude Code

Once installed you don't do anything special — just ask Claude to work in your repo. It gets the CodeCompass tools, and a hook redirects Grep to CodeCompass so the agent uses the index instead of scanning files (Glob stays available — CodeCompass searches contents and symbols, not file names). (Set CODECOMPASS_ENFORCE=0 to allow grep again.) The index builds automatically on first use for normal-sized workspaces and stays fresh as files change.

Large repos: a very large workspace isn't auto-indexed inside a tool call (that could stall). CodeCompass tells you to build it once from a terminal — see below — then it serves and keeps it fresh.

Using it from the command line

Linked roots (searching more than one repo)

When the code you work on spans more than one place — a shared library checked out elsewhere, a sibling repo, or a third-party drop on another drive that can't be nested under your project — linked roots let a project index and search those external directories alongside its own, as one federated result set. Each linked root keeps its own index (keyed by its absolute path, so a root two projects both link is indexed once and reused), is live-watched for edits like the main repo, and find_references/find_callees resolve across the boundary (C# via Roslyn; name matches search every root). Links are stored machine-local (absolute paths), not in the committed .codecompass.json.

Manage them from either side — they share one implementation:

From the agent (MCP tool):   manage_links  action: list | add | remove | focus   (path: for add/remove/focus)
From a terminal (CLI):       codecompass link add|remove|list <path> [project-dir]

Focus: linked several big repos but working in one? manage_links action=focus path="<repo>" scopes the session's searches to it (a folder name, path fragment or absolute path; comma-separated for several; no path clears it). Every scoped answer says what was excluded, and a focused root with no index yet is called out, so a narrowed search is never mistaken for "not found". Focus filters what's shown, not what's resolved.

Only the MCP server searches across linked roots (it's the long-lived process that holds each root's index open and watches it); the CLI always searches the single root you point it at. So: set federation up with manage_links or link add, then let the MCP tools do the multi-repo searching. codecompass doctor <project> lists every linked root, whether it exists and is indexed, and how many other projects share it.

Tuning for huge or generated trees

Indexing is robust on ordinary source at scale. The one hazard is large machine-generated files. Tree-sitter parse cost is linear in file size, but the constant factor varies ~70× by content (measured with parsebench): ordinary code parses at ~1.8 MB/s, while the worst case measured — deeply nested C++ templates — runs at ~0.1 MB/s (a 1 MB file ≈ 12 s). So a big degenerate file can take tens of seconds even though it grows linearly. That is bounded by default — symbol extraction is skipped above CODECOMPASS_MAX_SYMBOL_MB (1 MB), and those files are still fully trigram-indexed, so text search stays complete. In practice it never touches hand-written code: across the test corpora, every source file over 1 MB was machine-generated. Files skipped for a cap are counted and logged, so the coverage gap is visible rather than silent.

Two diagnostics quantify this on your own repo: codecompass symstats <path> reports the per-language file-size distribution (from stat only — free, so it is cheap on a huge repo) and runs tree-sitter, ignoring the cap, only on the largest ~100 files per language (sequential, timeout-guarded — it can neither hang nor crawl; add --full to parse everything) to show whether the big files yield symbols and where parse cost spikes; codecompass parsebench runs the synthetic size sweep above. A good maxSymbolMb sits above your largest real symbol-bearing file and below the size where parsing gets slow.

Environment variableEffect
CODECOMPASS_MAX_SYMBOL_MBSkip tree-sitter symbol extraction above this size (default 1). Raise it for large valid code whose symbols you want — safe from the data-blob crawl, since above 1 MB overwhelmingly numeric/hex files are auto-skipped for symbols by content.
CODECOMPASS_MAX_FILE_MBPer-file size cap for indexing entirely (default 2000 / 2 GB). Files ≥128 MB are streamed (bounded memory), so a high cap won't blow up RAM; lower it per-repo to skip big generated files. Its cost is read time on a full build.
CODECOMPASS_IGNOREComma/semicolon-separated directory names to exclude (e.g. generated,vendor).
CODECOMPASS_KEEPDirectory names to index even though they're skipped by default as build output (e.g. packages in a pnpm/yarn monorepo). Config: keepDirs. A zero result says when such directories were skipped.
CODECOMPASS_MAX_AUTO_MBWorkspaces larger than this (default 100) are left for a one-time CLI build instead of auto-indexing in a tool call.
CODECOMPASS_THREADS / CODECOMPASS_SEGMENT_MBIndexing parallelism / per-worker build-memory budget.
CODECOMPASS_READ_BUDGET_MBCap on total file bytes held in memory at once during a parallel build (default scales to RAM: ~1/16th of available, clamped 256 MB–4 GB). Stops N cores from each loading a multi-GB file at once when MAX_FILE_MB is large; an over-budget file reads solo.
CODECOMPASS_ENFORCE=0Allow the agent to use Grep again (the hook redirects it to CodeCompass by default).

Every knob also lives in an optional .codecompass.json at the repo root, so settings travel with the repo (precedence: env → config file → default). Fields: maxSymbolMb, maxFileMb, maxAutoMb, ignore (directory names), threads, segmentMb, compactSegments, stallWarnSec, readBudgetMb, autoReconcile, statusLine. Run codecompass survey <path> first: it reports what the caps skip, names the largest files, and suggests a change. It never auto-raises a cap; file size isn't a reliable signal of parse safety, so that call is left to the repo owner.

Staying fresh & status line

While Claude is running, a file watcher keeps the index current. Changes made outside a session — a Perforce/git sync, a branch switch with Claude closed — have no watcher to catch them, so on startup the server reconciles the loaded index against the current tree (a stat-walk vs. the last snapshot) in the background, while the old index keeps serving, then swaps. Automatic for local repos within maxAutoMb; deferred to a manual codecompass update for network shares and huge repos (a full-tree stat-walk is slow over SMB and the watcher is unreliable there). Force it with autoReconcile / CODECOMPASS_AUTO_RECONCILE (true/false).

CodeCompass can also show its state in Claude Code's status area. The server publishes state to a tiny per-repo file; the codecompass statusline command reads it. Add to Claude Code's settings.json: { "statusLine": { "type": "command", "command": "codecompass statusline" } }. Since setting any status-line command replaces Claude's built-in default, the bare command renders a self-contained line so you don't lose the usual info — Opus 4.8 · ~/CodeCompass · CodeCompass ✓ 48,000 files (states: … indexing 42%, ↻ refreshing…, ⚠ not indexed; the CodeCompass part drops in un-indexed repos). There is a single status-line slot — if you already have your own line, use --wrap "<cmd>": it forwards Claude's stdin, prints your command's output, and appends only the CodeCompass segment (not model/cwd — your command already shows those). Off with statusLine: false / CODECOMPASS_STATUS_LINE=0.

Diagnostics & bug reports

codecompass doctor <path> is a read-only health check: version, environment, config presence, index metadata (documents/segments, the version + time that built it), the cache-file listing, and pass/warn checks (builds? loads cleanly? current version? network path?). codecompass cache lists/GCs/clears the per-user cache by real repo path. codecompass report <path> zips the doctor snapshot + this repo's logs + its .codecompass.json for a bug report — and nothing from the source tree: it contains file paths/names and sizes (from logs), never file contents or index contents (--no-logs makes a paths-free bundle). Safe to run on someone else's proprietary code.

Limitations

Worth knowing where the edges are — all are by design and all skips are logged, never silent:

  • Files over MAX_FILE_MB (default 2000 MB / 2 GB) are absent from search entirely.
  • Files over MAX_SYMBOL_MB (default 1 MB), classified as numeric/hex data above 1 MB when the cap is raised, or streamed (≥128 MB), have no go-to-definition (still text-searchable).
  • Files ≥128 MB are indexed by streaming (bounded memory — a 2 GB file indexes even on 16 GB), removing the old ~1 GB single-string ceiling. A search into one uses a per-file block/positional index (a trigram Bloom filter per ~1 MB block) to read only the candidate blocks — a few MB, not the whole file — so a register lookup in a huge generated header stays cheap even over a network share. UTF-8 files; others fall back to a whole-file line scan.
  • #define/macro definitions are not captured as symbols (they'd explode the symbol index on register-map code); the names remain findable via search_code.
  • C/C++ references are matched by name, not compiled, so different symbols that share a name are listed together. No embeddings / semantic-meaning search. Single machine, single user.

Performance

Measured on: Intel Core i7-8700 (6 cores / 12 threads, ~2018), 32 GB RAM, Windows 11 Pro, .NET 10, with the EcoQoS / E-core throttling opt-out in effect. A modern many-core machine will be substantially faster to build.

The generated C/C++ corpus is a synthetic stress tree — 66,337 files / ~88 GB, single source files up to 1.4 GB — indexed once on local disk and once over an SMB/UNC share, to show behaviour at extreme scale and across a network.

How to read it:

  • search_code / find_definition / search_symbols are index-backed: warm they answer in ~1–100 ms on every repo (even 132 k files, even over SMB). Cold is dominated by process start + map-open (~0.2–2 s) — exactly what the persistent MCP server amortizes away.
  • find_references on C# builds Roslyn's workspace once (the refs 1st-call), then keeps it resident. Its cost then depends on the name: one with a single declaration answers in about a second warm, while a name declared many times over (Equals, GetEnumerator) runs one whole-solution search per unrelated declaration and can take tens of seconds — the max column.
  • find_references on C/C++ (and Python, TypeScript, …) is a name search over the index, so it costs about what search_code does plus reading the matched files to skip comments and strings: well under a second warm on the public repos. On the generated corpus, whose matched files run to gigabytes, that reading dominates — about half a second warm on local disk, a couple of seconds over SMB.

At ~25 MB/s a first index of a dozens-of-GB repo is on the order of minutes-to-tens-of-minutes (less on a many-core machine), and searching it afterward uses only a few hundred MB of RAM — comfortably within a 16 GB laptop.

Scale check (10 GB / ~1.1 million files): an aggregated 10.4 GB corpus indexed in 7m48s (22 MB/s) on the machine above, using 792 MB heap / 2.2 GB peak working set during a full build-plus-edit cycle. Queries stayed ~1 ms (p95 7.9 ms). Memory stays bounded because the trigram and symbol indexes — and the change-detection ledger — are all memory-mapped on disk, not loaded into RAM, so searching a repo this size uses only a few hundred MB and editing it keeps just the changed files in memory. First-time build memory is tunable via CODECOMPASS_SEGMENT_MB / CODECOMPASS_THREADS.

Logs & troubleshooting

CodeCompass keeps a self-limiting log on disk so problems can be diagnosed after the fact without watching it live. Everything lives in one folder — run codecompass logs to print the location and the current files:

%LOCALAPPDATA%\CodeCompass\logs\
  codecompass.log              common log: startup + every warning/error, all repos
  repo-<name>-<key>.log         per-repo log: full detail (builds, incremental reindex, skips)

Each file is size-capped and rotated (default 5 MB × 4 files kept), so the logs can never grow unbounded — at most ~20 MB per file family. Warnings and errors from a repo are mirrored up into the common log, so that one file is the first place to look when something's off.

SettingEffect
CODECOMPASS_LOG_LEVELoff / error / warn / info (default) / debug
CODECOMPASS_LOG=0disable logging entirely
CODECOMPASS_LOG_DIRwrite logs somewhere other than the default folder
CODECOMPASS_LOG_MAX_MBrotate each file at this size (default 5)
CODECOMPASS_LOG_KEEPhow many rotated files to keep (default 3)

Logging never throws and never blocks indexing or search — if the log can't be written it's silently skipped. Set CODECOMPASS_LOG_LEVEL=debug to record per-file skips and detailed build stats when chasing a specific issue.
