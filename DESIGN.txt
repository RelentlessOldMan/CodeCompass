CodeCompass
===========

A fully-local code search and retrieval engine that gives AI coding agents
(Claude Code first) fast, precise "code smarts" over very large polyglot
codebases, so the agent stops burning tokens reading whole files and grepping
blindly.

Status: built and in use. All six build phases below are complete, plus a long
tail of hardening for scale. This document is both the north star and a record
of the design decisions - especially the ones learned the hard way while making
indexing survive very large, partly machine-generated codebases. Where a
decision has a non-obvious "why", it is written down here, because the reasons
matter more than the code. The build carries a git-derived version
(1.0.<commit-count>+<short-sha>, reported by `codecompass version` and in the
logs) so a user's report pins an exact commit.


The problem
-----------

When an AI coding agent needs to understand code, its default moves are cheap
but wasteful: grep for a string, then read entire files to figure out what
matched. On a small repo that's fine. On ours - dozens of GB, dominated by C#
and C/C++ with some Python, MATLAB, and other - it is slow and it eats an
enormous number of tokens. Every full-file read is context the model pays for,
most of which is irrelevant to the question it was actually asking.

The agent doesn't need the whole file. It needs the right few lines: this
function's definition, everywhere this symbol is used, the handful of snippets
that actually match. Delivering exactly that - and nothing more - is the entire
point of CodeCompass.

Recent public results back this up. A 2026 study (Codebase-Memory) measured
roughly 10x fewer tokens and about 2.1x fewer tool calls when an agent queried
a structural code index over MCP instead of reading files directly. Other
tree-sitter based tools report up to ~99% token reduction versus sending whole
files. The direction is not in doubt; the exact number will depend on our
workloads.


Goals
-----

- Cut the tokens an agent spends locating and understanding code, by returning
  ranked snippets, line ranges, and symbol locations instead of whole files.
- Be genuinely fast to index at scale. Dozens of GB is the target. Indexing
  speed is a first-class requirement, not an afterthought.
- Treat C# and C/C++ as first-class citizens with real semantic understanding
  (accurate go-to-definition and find-all-references), not just text matching.
- Support the rest (Python, MATLAB, and others) well enough to be useful, via
  syntactic parsing.
- Run entirely on the local machine. No code ever leaves it. No GPU. No cloud
  API. This must run well on ordinary work laptops.
- Keep the index fresh automatically. When files change (a "get latest" from
  source control, a branch switch, an edit), re-index what actually changed -
  and only what actually changed. Ignore noise.
- Be trivial to install and use. Someone grabs a binary or runs one install
  command and it just works, with no knowledge of what's inside.
- Make the agent prefer CodeCompass over grep automatically, every time, with
  grep as a fallback only when CodeCompass genuinely can't help.


Non-goals (for v1)
------------------

- No embeddings / vector / semantic-meaning search in v1. The evidence is that
  vector-only retrieval is both heavier (wants a model, often a GPU) and weaker
  for real agentic code navigation than people assume - state-of-the-art
  embedding models lose roughly 70% of their accuracy moving from toy
  benchmarks to real repository navigation, and Anthropic themselves removed
  vector search from Claude Code in mid-2025 in favor of plain grep. Embeddings
  are deliberately deferred to a possible v2, as an optional bolt-on only, and
  even then would use a small CPU model, never a GPU.
- No web UI. This is an engine plus an agent integration, not a portal.
- No multi-user server product. Local, single-machine, single-developer.


Locked decisions
----------------

These are settled and drive everything below.

- Implementation stack: .NET / C#. Reasons: the best C# semantics come from
  Roslyn, which is native .NET; the best C/C++ semantics come from clang, which
  is reachable from .NET via ClangSharp or by driving clangd; the official MCP
  SDK for C# is first-party; .NET publishes single-file, self-contained, native
  Windows binaries (the "grab it and go" requirement); and it is a stack the
  author can maintain. .NET's performance with memory-mapped files, fast
  directory enumeration, parallelism, and spans is more than adequate for
  trigram indexing at this scale.

- Retrieval approach for v1: lexical + symbolic only. A fast trigram text index
  plus structural symbol understanding. No model in the hot path.

- Change detection: file-based, source-control-agnostic. We do not special-case
  Git or Perforce or SVN. We watch the filesystem and diff content hashes. This
  catches everything - a get-latest, a branch switch, a manual edit, a script
  that rewrites files - without caring how it happened.

- Enforcement: hard block plus fallback. A Claude Code hook intercepts the
  agent's grep/glob calls and redirects them to CodeCompass. Grep is only
  allowed through when CodeCompass legitimately does not apply.

- Distribution: packaged as a Claude Code plugin, so a single install wires up
  the search engine, the enforcement hook, and the agent instructions together.


Architecture
------------

Think of it as an agent-facing front door, a background brain that owns the
index, and the intelligence layers underneath.

The agent side. Claude Code talks to CodeCompass over MCP - the standard way to
give an agent custom tools. CodeCompass exposes exactly five tools, deliberately
kept minimal so the tool surface itself costs the agent almost no tokens to carry:
search_code (ranked text matches with line ranges), find_definition (where a
symbol is defined), find_references (everywhere a symbol is used), search_symbols
(find symbols by name), and reindex (refresh the index on demand). Alongside the
MCP server, a hook watches for the agent trying to grep or glob and steers it to
CodeCompass instead. Everything else the tool can do - survey, symstats,
parsebench, logs, version - is CLI-only, so it never enlarges the agent's tool set.

The brain. A background indexing service owns the on-disk index and keeps it
current. It walks the tree, filters out junk, watches for changes, detects what
truly changed, and updates the index incrementally. The MCP server queries this
brain; the brain does the heavy lifting once and answers many times.

The intelligence layers, cheapest first:

- Lexical layer. A positional trigram index (the same idea Sourcegraph's zoekt
  uses) for fast substring and regex search across everything. The design
  target is roughly the corpus size a few times over on disk, but only a small
  fraction of the corpus in RAM, because the bulk lives in memory-mapped files
  on the SSD rather than in memory. Pure CPU, no model.

  A query is broken into trigrams; a document is a candidate only if it holds
  ALL of them, so search intersects the per-trigram posting lists and then reads
  only the surviving candidates to confirm and get line:col. The intersection
  fetches every trigram's list first, then intersects starting from the RAREST
  (shortest) one - the running set can't grow past the smallest input, and if
  any trigram is absent the whole segment is skipped before any intersection
  work. This is invisible on ordinary queries (dominated by reading candidate
  files) but a large win on the pathological case that matters at scale: a
  specific long identifier in a huge generated-code repo, whose leading trigrams
  are near-universal but whose conjunction is rare - measured ~35% faster than
  query-order intersection on a 100k-file synthetic of exactly that shape, and
  the margin grows with document count.

- Syntactic layer (all languages). Tree-sitter parses every supported language
  into a syntax tree, giving us symbol names, definitions, and clean chunk
  boundaries. This is what makes Python, MATLAB, and the long tail useful, and
  it is the baseline for C# and C++ too. Most grammars come from the
  TreeSitter.DotNet package; a grammar it doesn't ship (e.g. Lauterbach TRACE32
  PRACTICE, .cmm) is added by vendoring the grammar's MIT C sources under
  grammars/, building them to a native DLL (grammars/build-t32.ps1, committed so
  a normal build needs no C compiler), and registering the extension + a capture
  query in LanguageRegistry. A grammar that can't load (wrong arch, missing DLL)
  degrades silently to text-only search - never an error.

- Semantic layer for C# (Roslyn). Precise, cross-file understanding for C#:
  real find-all-references, go-to-definition, call hierarchy across a solution.

- Semantic layer for C/C++ (clang). Precise understanding when a compile
  database (compile_commands.json) is available. When it isn't, we degrade
  gracefully to the syntactic layer plus trigram heuristics rather than
  pretending to be exact. C++ is honestly the hardest language here and we treat
  it with the respect it deserves.

- Semantic analyzers are the one part NOT memory-mapped: Roslyn holds a whole
  in-memory solution (every .cs file's text, plus a cached compilation once
  find_references runs) and clang holds its keyed declaration/reference model -
  hundreds of MB to GB on a large repo. They are built LAZILY (only when
  find_references is first called) and, on a long-lived server, EVICTED after a
  stretch with no semantic query (default 10 min; CODECOMPASS_SEMANTIC_IDLE_MIN /
  semanticIdleMinutes, 0 = keep resident). Eviction disposes the Roslyn workspace
  and clears clang's maps, then they rebuild lazily on the next use - so a session
  that greps and reads but stops resolving symbols doesn't pin memory it isn't
  using. Eviction takes the same write lock a rebuild does, so it can never dispose
  an analyzer mid-query (a find_references holds the read lock for its whole
  duration). The clang line-context cache is now per-query (freed when the query
  returns) rather than a resident field that grew with every file ever returned.
  This is the counterpart to the mmap'd trigram/symbol indexes: everything that
  scales with repo size is either mmap'd or reclaimable.


Keeping the index fresh without churning on noise
-------------------------------------------------

This is as important as the search itself, and it is where "smart" is earned.

- A filesystem watcher notices changes as they happen.

- Events are debounced and batched. A get-latest that touches ten thousand
  files triggers one re-index pass over a short quiet window, not ten thousand
  frantic passes.

- Change is confirmed by content hashing, organized as a Merkle tree (the same
  technique Cursor uses). A file that was touched but whose content is identical
  is skipped. Only files whose actual content changed get re-indexed, and the
  hash tree lets us find them by walking only the branches that diverged rather
  than rehashing the world.

- Junk is filtered before it ever enters the index: honor .gitignore, plus a
  built-in blocklist for build output and noise (bin, obj, node_modules,
  compiled objects, generated files, binaries). This is what stops the index
  from filling with garbage.

- The index is persisted on disk (memory-mapped, updated safely) so restarting
  never means re-indexing dozens of GB from scratch.

- The change-scan reads each file's size and mtime from the DIRECTORY ENUMERATION
  itself (EnumerateFileSystemInfos pre-fills and caches them from the one listing),
  not from separate per-file stats. Locally that's a wash, but over an SMB share each
  stat is a network round-trip: the old "list names, then stat each file for size, then
  stat again for mtime" paid ~2 extra round-trips per file, which on a 43k-file share
  was the entire ~5-minute no-op `update`. Reading metadata off the enumeration collapses
  that to ~one round-trip per directory. (You can't scan fewer files: a directory's mtime
  only moves on add/remove/rename, so an in-place content edit - the common case - is
  invisible at the directory level; every file's own timestamp must be read.)
  The walk also reads directories CONCURRENTLY (default min(cores, 8) workers, a
  bounded producer/consumer that still streams lazily so a builder paces it). SMB2's
  credit flow-control lets many enumerations be in flight on one connection, so this
  overlaps the remaining per-directory round-trips on a latency-bound share; it's a
  wash locally. Set walkThreads=1 (or CODECOMPASS_WALK_THREADS=1) for a serial walk.

- The change-detection ledger (path -> size/mtime/hash for every file) is itself
  kept on disk, not in RAM: an immutable, memory-mapped, path-sorted base file
  answers lookups by binary search, while recent edits live in a small in-memory
  overlay that is journaled and periodically folded back into a fresh base
  (compaction). This is what keeps active editing of a dozens-of-GB repo cheap on
  memory - a handful of changed files never pulls the whole ledger into RAM. Base
  files use monotonic, never-reused numbers so a rewrite is safe while a previous
  mmap is still held (the same discipline the trigram/symbol segments use).

- A very large change (say a branch switch that rewrites most of the tree) can
  fall back to a full rebuild when that is faster than a huge incremental diff.

- The watcher only covers changes made *while a session is running*. Changes made
  outside a session - a Perforce/git sync with Claude closed, a branch switch in
  another terminal - have no live event to catch them. So on startup, after loading
  an existing index, the server RECONCILES it against the current tree in the
  background (a stat-walk vs. the last snapshot), while the loaded index keeps
  serving reads, then swaps atomically. This is gated: automatic for local repos
  within the auto-index limit; deferred to a manual `codecompass update` for network
  shares and huge repos, where a full-tree stat-walk is slow over SMB and the
  watcher is unreliable anyway. The `autoReconcile` config / CODECOMPASS_AUTO_RECONCILE
  env forces it on or off. This is the mechanism that catches "I synced while Claude
  was closed" without making the user remember to reindex.


Letting the user see what it's doing (status line)
--------------------------------------------------

Long operations - an initial background build, a startup reconcile - must be
visible, not silent. The reliable channel to the agent is tool-result text (a
search during a build returns a "still indexing NN%" message rather than
blocking). For the *human*, CodeCompass can also publish to Claude Code's status
line: `CodeCompass ✓ 48,000 files`, `… indexing 42%`, `↻ refreshing (external
changes)…`.

The wrinkle is that Claude Code's status line is a separate short-lived process
that can't see the server's memory. So the state is bridged through a tiny
per-repo `status.json` in the local cache: the server writes it on every state
transition (best-effort, offloaded so it never stalls indexing), and the
`codecompass statusline` command reads it. The command reads Claude's stdin JSON
(`workspace.project_dir` / `cwd` for the repo, `model.display_name` for the model)
and resolves that repo's status file WITHOUT creating anything (it runs on every
render, in every folder).

Setting any status-line command REPLACES Claude Code's built-in default outright,
so the bare command is a self-contained default: it renders `<model> · <cwd> ·
CodeCompass <state>` - you don't lose the model/cwd you'd otherwise have. The
CodeCompass part is dropped in repos we've never indexed, so the line gracefully
degrades to `model · cwd` rather than going blank.

Claude Code has a single status-line slot. A user who already has their own status
line uses `--wrap "<cmd>"`: we forward the same stdin to their command, print its
output, and append ONLY our segment - deliberately NOT re-adding model/cwd, since
their command already shows them (no duplication). Publishing is on by default and
disabled with `statusLine: false` / CODECOMPASS_STATUS_LINE=0.


How it saves tokens
--------------------

The saving does not come from clever search alone - it comes from the shape of
what we hand back. Instead of the agent reading a 2,000-line file to find one
function, CodeCompass returns that function's definition and its exact line
range. Instead of grepping and then opening ten files to see the matches in
context, it returns the ranked matching snippets directly. Symbol lookups
replace file reads. The agent gets the signal without the surrounding noise it
would otherwise pay for.


Honest results (never a confident wrong answer)
-----------------------------------------------

An index that quietly omits things is worse than no index: an agent that reads a
false "not found" may delete a caller that in fact exists. So results disclose
their own limits (a principle shared with the ripwire project's "honesty
contract"):

- Truncation is a floor, not a total. A capped result says "showing the first N;
  MORE EXIST" and the counts distinguish an exact total from a capped one, so the
  agent knows whether to narrow rather than trusting a partial list as complete.

- A zero means "none found," not "none exists." Files excluded by the size cap
  aren't searched at all, so when a search returns nothing and the repo has such
  files, the result says so ("N file(s) exceed the size cap and are NOT indexed -
  a match could be in one"). The count is recorded in the per-repo meta at build
  time; `survey` itemizes exactly which files, and `doctor` reports it.

- The SAME false-negative has a second door, and it's disclosed too. A file can be
  fully text-searchable yet have NO symbols extracted - it's over the symbol cap, a
  numeric data blob, or streamed (>=128 MB). So a go-to-definition could genuinely
  live in a large generated file that find_definition/search_symbols can't see. A
  separate per-file count (recorded at build time, next to the size-cap count) makes
  those two tools disclose it on an empty result ("N large/generated file(s) are
  text-searchable but had NO symbols extracted - a definition could be in one; try
  search_code"). It's scoped to the symbol tools: search_code already covers those
  files, so it doesn't repeat the note. The count is file-level (classified when the
  file is read), so it costs nothing on the per-symbol hot path; an incremental
  update carries the last full build's value forward (a full reindex refreshes it).

- The C/C++ semantic layer discloses when it ran degraded. Precise C/C++ references
  need a compile_commands.json; without one, clang runs on best-effort flags with
  unresolved includes/defines and may resolve little or nothing. A bare "0 C/C++
  semantic" would read as "no references exist," so find_references appends a note
  ("no compile_commands.json found - ran best-effort over N translation units, may be
  incomplete; add one for precise results"), and `doctor` warns when C/C++ sources are
  present with no compile DB. The dialect is chosen by extension (gnu11 for .c, not
  c++17) so valid C isn't rejected on the very repos that lack a compile DB. A compile
  DB outside the two default probe spots (root, root/build) is found via the
  `compileCommands` config (or CODECOMPASS_COMPILE_COMMANDS) - a list of files or dirs,
  merged per source file so a multi-target build (one DB per target) is covered; the
  first DB to describe a file wins a collision (any valid parse binds the symbol - we
  don't reproduce a target's object code). This is the same honesty contract as the
  size-cap disclosure, applied to semantic availability.

- Empty results also point at the next tool (case-insensitive retry, search_code
  for a macro/unsupported language, etc.) instead of dead-ending.

- Output is deterministic: the same repo yields the same results and the same
  trigram-posting count run to run (order-independent), so a diff is a real change.


Why not just use something that already exists
----------------------------------------------

We surveyed the landscape. Three camps exist, none of which meets all the
requirements:

- Embedding / vector MCP tools (for example zilliztech/claude-context and
  several local-embedding forks). These use exactly the approach we ruled out:
  they want a model, and vector-only retrieval underperforms for real agentic
  code navigation.

- Tree-sitter / syntactic MCP tools (for example CodeSight-mcp and the
  Codebase-Memory research project). Local, no model, and token-efficient -
  this is essentially our syntactic layer - but they are syntactic only (no
  Roslyn/clang cross-file semantics) and are not built for dozens-of-GB trigram
  scale, smart file-based reindexing, or grep enforcement.

- LSP-based semantic MCP, above all oraios/serena. This is the closest existing
  thing to the vision: local, MCP, symbol-level semantic tools driven by real
  language servers (clangd for C/C++, a C# server, twenty-plus languages). It is
  worth evaluating directly before we build. Its likely gaps for us: language
  servers are heavy to start and were not designed to index dozens of GB, there
  is no fast lexical/trigram layer for raw text search at scale, and there is no
  built-in mechanism to force the agent off grep.

Conclusion: no off-the-shelf tool combines .NET-native Roslyn for C#, clang for
C++, trigram search at scale, file-based smart incremental reindexing, and
hard-block grep enforcement in one easy-to-install local package. That
combination is CodeCompass's reason to exist.

Decision: we build our own, greenfield. We deliberately skip adopting or forking
an existing tool. We still borrow proven designs where they fit - zoekt's
positional-trigram index, Cursor's Merkle change detection, tree-sitter for
parsing - but the codebase is ours.


Build phases
------------

1. Walker, content hashing/Merkle, trigram index, and a plain command-line
   query. Goal: prove fast indexing and search on a real repo. No agent yet.

2. Tree-sitter syntactic symbols across all languages: definition lookup and
   symbol search.

3. MCP server exposing search_code, find_definition, find_references,
   search_symbols, and reindex. Wire it into Claude Code manually and feel the
   difference.

4. Semantic layers: Roslyn for C#, then clang/ClangSharp for C/C++.

5. Filesystem watcher with debounced, hash-verified incremental re-indexing.

6. Package as a Claude Code plugin: bundle the MCP server, the hard-block
   grep-redirect hook, and the agent instructions into a one-command install.

All six phases are complete. Beyond them, the bulk of the work has been hardening
for scale and correctness: on-disk memory-mapped trigram and symbol indexes, an
on-disk change-detection snapshot, RAM-scaled build and read budgets, in-index
segment compaction, opting out of Windows E-core/EcoQoS throttling during a build,
a per-repo .codecompass.json config, the diagnostics (survey/symstats/parsebench),
and the large-file/generated-code handling described under "Scaling, huge files,
and generated code". Correctness is guarded by a growing unit-test suite
(150-plus tests) including the pathological cases that once broke indexing.


Diagnostics and logging
-----------------------

Because CodeCompass runs unattended on other people's machines (a very large,
tens-of-GB repo, inside Claude Code where its stderr is invisible), it keeps a self-limiting
log on disk so a problem can be diagnosed after the fact. Everything lives in one
folder, %LOCALAPPDATA%\CodeCompass\logs, alongside the index caches, so there is a
single place to look or clear.

There are two views. A common log (codecompass.log) carries process lifecycle plus
every warning and error from any repo, so it is the first place to look when
something is off. Per-repo logs (repo-<name>-<key>.log) carry that repo's full
detail: builds, incremental reindex batches with counts, the size-gate decision,
and, at debug level, per-file skips and build statistics. A repo's warnings and
errors are mirrored up into the common log so nothing important is hidden in a
per-repo file.

The hard rule is that the log can never itself become a problem. Every file is
size-capped and rotated (default 5 MB, keeping 3 old files), bounding each family
to about 20 MB regardless of how long the server runs. Logging never throws and
never blocks indexing or search: if a line cannot be written it is silently
dropped. Level and limits are environment-tunable (CODECOMPASS_LOG_LEVEL, _MAX_MB,
_KEEP, _DIR; CODECOMPASS_LOG=0 disables it). The default level is info; debug is
opt-in for chasing a specific issue. The CLI exposes "codecompass logs" to print
the folder and current files.


Linked roots (federated multi-index)
------------------------------------

A project sometimes needs to search code that can't be nested under it: a shared
library checked out elsewhere, a sibling repo, a third-party drop on another
drive. "Linked roots" attach such external directories to a project and serve
them as one federated result set. The design choices, and their whys:

- Federated multi-index, not one combined index. Each linked root keeps its OWN
  independent on-disk index, keyed by its absolute path, exactly like any repo.
  The server queries the project index plus every linked index and merges the
  results. This reuses all the single-root machinery unchanged, and - the reason
  it matters - a root shared by two projects is indexed ONCE and referenced by
  both. Unlinking is just dropping it from a list; the shared index survives while
  any project still references it (reference-counted by scanning the per-user
  cache for other projects' links).

- Links are machine-local. The linked paths are absolute and machine-specific
  (Z:\..., another checkout), so they are stored as links.json in the PROJECT's
  cache dir under %LOCALAPPDATA%, NOT in the committed, portable .codecompass.json.

- Same freshness as the project root - this was a correction during design. The
  primary real use is a huge repo over a network whose linked roots are actively
  edited, so a linked root must get the SAME change-handling as the main repo:
  live file-watching for local roots and the same startup reconcile (gated for
  network/huge) otherwise. A linked root is not a static snapshot.

- One writer per shared index, via a crash-proof lock. Two sessions that share a
  linked root (two windows, or two projects) must not both mutate its one cache
  dir. Ownership is an OS-held EXCLUSIVE FILE HANDLE (FileShare.None) on a
  .writer.lock in the cache dir - NOT the file's contents. The claim exists only
  while the process holds the handle open, so a crash / kill / shutdown / power
  loss releases it automatically (the kernel closes handles on process death; on
  power loss the handle table is RAM and simply gone). There is no PID, heartbeat,
  or TTL to go stale, and a leftover lock file is inert because ownership is tested
  by trying to open it exclusively, not by its existence. The cache is always local
  (%LOCALAPPDATA%), so this is a single-machine NTFS lock where share-modes are
  reliable; different machines have separate caches and never contend. The session
  that wins ownership live-watches and reconciles the root; a session that doesn't
  serves it read-only from the owner's kept-fresh index.

- Live link-set reconcile, off the index lock. links.json lives in the project's
  cache dir, which is always LOCAL, so a stat is sub-ms: each query compares its cheap
  signature (mtime^length) to the last seen one and reconciles only on a change - so a
  link add/remove done in a terminal is picked up WITHOUT restarting the session. The
  reconcile is a safe DIFF: roots already served keep their index, ownership, and
  watcher untouched, and only the delta is added/removed. This is deliberate - blindly
  reloading would re-TryAcquire ownership of a root we already hold, which fails against
  our OWN exclusive handle and would demote us to reader. A transient unreadable read
  (racing the atomic write) keeps the current set rather than reading a momentary empty
  as "all links removed". All linked-root lifecycle is serialized by a dedicated gate
  and never runs while holding the index RW lock: a RepositoryWatcher.Dispose drains an
  in-flight callback that itself takes the RW lock, so watchers are created/disposed
  OFF-lock and only the mmap handles are swapped under a brief write. The lock order
  is always gate-then-RW, never the reverse, so there is no AB-BA hazard with reads.

- Cross-root code intelligence. find_references and find_callees resolve ACROSS the
  boundary: the Roslyn (C#) and clang (C/C++) analyzers span the project root AND
  every linked root in ONE compilation / USR model, so a call in the project to a
  type defined in a linked root binds. A per-root union would MISS this - the
  project compilation alone has no source for the linked type - which is why one
  spanning compilation is worth the cost. Each semantic result carries the absolute
  root it belongs to, so a hit is addressed correctly. The analyzers are rebuilt
  lazily when the root set changes or a linked root's content changes.

- Result addressing. Project (primary) hits stay repo-relative for compactness; a
  hit from a linked root is shown as its ABSOLUTE path, so it is unambiguous and
  directly readable. Reads resolve through the owning root, guarded by PathSafety.

- Guards. A directory inside the project (or inside/around an existing link) is
  rejected - it's already covered. The pathological subst/drive-alias aliasing case
  is deliberately out of scope.


Scaling, huge files, and generated code
---------------------------------------

Most of the hard problems in this project were not about search quality; they
were about surviving very large, partly machine-generated trees without hanging,
crashing, or exhausting a laptop's memory. The design below is the answer, and
the "why" behind each piece is the point.

Memory is bounded regardless of repo size. Both indexes (trigram and symbol) are
built by streaming to disk in segments at a byte budget and then read back
through memory-mapped files, so neither building nor searching holds the whole
index in RAM. The change-detection ledger is on disk too (mmap base + small
in-memory overlay, described above). The per-build segment buffers are sized to a
fraction of available RAM, and the amount of file content read at once is capped
by a budget that also scales to RAM. The result, measured on a tens-of-GB repo:
a first build fits in a few GB of RAM and search fits in hundreds of MB, on an
ordinary 16 GB machine. Memory does not grow with the size of the index.

The in-flight read budget deserves a note, because "scaled to RAM" is more subtle
than it looks. A worker that indexes a text file briefly holds the raw bytes and
the decoded UTF-16 string at the same time - about 3x the file size. So the
budget reserves ~3x a file's size before reading it, which makes the RAM math
honest: a budget of N genuinely fits a file up to ~N/3, and a file larger than
the whole budget reserves all of it and is processed alone (blocking others until
it finishes, never deadlocking). This is what stops N cores from each pulling a
multi-hundred-MB file simultaneously and blowing up memory when the file cap is
raised. The budget throttles concurrency, not single-file size: a big file still
indexes, it just runs solo.

Two coverage caps, and why they exist. Both are visible, tunable, and logged
(never silent), and `codecompass survey` reports exactly what they skip.

- File cap (CODECOMPASS_MAX_FILE_MB, default 2 GB). Above this, a file is not
  indexed at all. The default is high because large files now stream (bounded
  memory) rather than being read whole, so a big cap no longer risks RAM; its cost
  is read time on a full build. Lower it per-repo when you don't want big generated
  files indexed - enormous generated data/bundle files add almost nothing to a
  trigram index anyway (trigrams deduplicate such repetitive content down to a
  rounding error, so the index barely grows even as bytes read climb). The cost of
  including them is read time, not index size.

- Symbol cap (CODECOMPASS_MAX_SYMBOL_MB, default 1). Above this, a file is still
  fully text-searchable but gets no symbol extraction (no go-to-definition). Why:
  parse cost. See below.

Parse cost is linear - but the constant varies ~70x by content. This corrects an
earlier assumption. We first believed tree-sitter parsing was ~O(n^2) on dense
generated content; direct measurement (the `parsebench` sweep) disproved that -
parse time grows linearly with file size for every content shape tried. What
varies enormously is the constant factor. Ordinary source parses at ~1.8 MB/s;
the worst shapes are far slower: deeply nested C++ template expressions at
~0.1 MB/s, and - the one that matters in practice - large machine-generated
numeric "data-blob" files at ~1 MB/s, roughly 25x slower than code.

The data-blob problem, and the crawl it caused. The real hazard at scale turned
out to be large, machine-generated numeric data files: test-vector and data-buffer
sources that are essentially one giant array initializer of hex or decimal
literals. They have three bad properties at once - multi-MB size, ~25x-slow parse
(a million tiny numeric tokens make a huge parse tree), and zero extractable
symbols. On a real tens-of-GB tree, raising the symbol cap so these got parsed
made a build "crawl": it raced to ~99% then wedged for minutes. A thread-stack
capture of the wedged process settled what it was - roughly all worker threads
parked in native tree-sitter parse of these files. Not a lock, not garbage
collection, not a finalization step, and not scheduling (switching the work
partitioner to hand out one file at a time made no difference, because the slow
files are simply slow, not badly balanced). It is parallel native parse of files
that are expensive and worthless to parse.

How we handle it, in layers:

- At default settings the problem cannot occur. Every one of these data-blob files
  is larger than 1 MB, so the default symbol cap already skips all of them, and
  the crawl never happens. This is not luck: measured across large corpora,
  essentially every source file over 1 MB is machine-generated, and effectively
  all files that contain real, extractable symbols are under 1 MB. So the 1 MB cap
  costs almost nothing in real symbol coverage while removing the entire hazard.

- If the symbol cap is raised (to get symbols out of large hand-written code),
  a fixed, non-configurable content check engages, but only for files above 1 MB
  - i.e. only for the files a raised cap newly admits. It skips symbol extraction
  when a file is overwhelmingly numeric/hex data. The signal is cheap and robust:
  the density of letters that fall outside numeric-literal context. Hex digits
  (a-f/A-F) and the "0x" prefix (x/X) are not counted; every other letter is.
  Real code and even register-map #define headers are full of such letters
  (roughly 25-40%); a numeric/hex data array has almost none (~0%). Below 1 MB the
  check never runs, so it has zero cost and zero behavioral effect at defaults.
  The effect: raising the cap now safely parses large real code while the data
  blobs that cause the crawl are skipped by content, not by size.

- Register-map #define headers are a different generated shape and are treated
  differently. They parse fast, so they are not a performance problem - but they
  are also almost pure `#define` lines, and we deliberately do NOT capture
  `#define`/macro definitions as symbols. On a register-map-heavy codebase that
  would mint millions of symbol entries and bloat the symbol index for little
  value; those names remain findable as text via search_code. This is a conscious
  trade, revisited and re-affirmed.

- Load balancing is general hygiene, not the fix. Workers pull one file at a time
  rather than in growing chunks, so a directory-order cluster of expensive files
  (say a vendored, minified bundle directory) can't strand a single core while the
  rest idle. This helps genuinely clustered cost; it is explicitly not what tames
  the data-blob crawl (that is the caps above).

- A watchdog makes any residual stall visible and diagnosable. It runs on a
  dedicated thread - not a pool timer, which would itself be starved during a
  build that saturates the thread pool (that starvation is why an earlier
  timer-based watchdog stayed silent). It fires when byte progress freezes or when
  any worker has held a single file longer than the stall window, and it logs the
  exact file(s) in flight and how long each has been held - naming the culprit
  rather than guessing, or reporting "no files in flight" if a stall is instead in
  a post-parse step. A concise notice is also printed to stderr so a freeze is not
  a silently stuck progress bar.

Very large single files: streamed, not read whole. The naive approach reads each
file into one byte array and decodes it into one .NET string - which imposes two
platform ceilings no amount of RAM removes: a single array fails above 2 GB, and a
single string tops out near ~1 GB of text (its UTF-16 buffer hits the 2 GB
single-object limit at ~1 billion characters). Rather than skip files past that
ceiling, files at or above a threshold (~128 MB) take a streaming path: the file
is read in ~1 MB chunks, hashed incrementally, decoded incrementally (BOM-aware, to
match the normal decoder), and its distinct trigram set is accumulated with a
two-char carry across chunk boundaries. Peak memory is bounded by the chunk plus
the trigram set, not the file size - so a 2 GB file indexes even on a 16 GB
machine, and the only real ceiling becomes the file cap itself (default 2 GB;
raise it and streaming will still cope). The streamed trigram set is identical to
the whole-file result, so a file indexes the same whichever path it takes.

Symbols are the one thing streamed files give up: tree-sitter parses a single
in-memory string (the same ~1 GB limit, and streaming a parser is a different
beast), so streamed files get trigram text search but no symbol extraction - which
is consistent with the symbol cap and fine in practice, since multi-hundred-MB
files are generated data with ~no useful symbols.

Searching large files without re-reading them: the block/positional index. The
trigram index is only a candidate filter, so confirming a match and reporting its
line:col means reading the candidate file - and re-reading a multi-GB file per query
would be ruinous over a network share (and it is exactly the case that matters:
a 2 GB auto-generated register-map header IS the identifiers you search for, so it
is a candidate on essentially every such query). To avoid that, indexing a large
file also builds a positional sidecar in the local cache: the file is cut into
line-aligned ~1 MB blocks, and each block stores its first line number, byte range,
and a trigram Bloom filter. A search consults the (small, local) sidecar, keeps only
the blocks whose Blooms admit ALL the query's trigrams, and reads just those blocks
from the source - a few MB, not the whole file. The Bloom has no false negatives, so
a real match is never skipped; false positives only cost an extra block read that
the scan then discards. Requiring all query trigrams in one block is what makes the
common-prefix case (every macro starting HEY_MOM_MY_CHIP_...) cheap: the distinctive
suffix trigrams are the selective ones, and a prefix-only query that legitimately
matches everywhere is bounded by stopping at the result limit. Full per-occurrence
positional postings were rejected: for a multi-GB file the positions can exceed the
file size. The sidecar is UTF-8 only (line detection needs byte 0x0A to mean
newline); a non-UTF-8 large file falls back to a whole-file line scan. A missing or
invalid sidecar always falls back too, so it is an optimization, never a correctness
dependency.

Verifying normal candidates over a share: the same "trigram index is only a candidate
filter" fact means every query still reads its candidate files to confirm the match and
report line:col. On a local disk that is cheap and done serially (stop the instant the
result limit is hit). Over an SMB share each read is dominated by round-trip latency, and
reading candidates one at a time stacks that latency linearly - so when the root is a
network path the verify runs BOUNDED-PARALLEL (default min(cores, 8), the walkThreads
knob), overlapping the reads the way the walk overlaps enumerations. Results are merged
back in candidate order, so the output is byte-identical to the serial path - only faster;
the parallel path just reads up to one window ahead, trading a few possibly-wasted reads
for latency hiding (a good trade only when latency dominates, hence the network gate).
Two round-trips per candidate also became one: a file's large-vs-small decision is read
from the LOCAL sidecar's presence instead of a network stat, and normal files read their
size off the already-open handle rather than a separate stat before the open. Source reads
open with a large buffer + sequential-scan hint on a share (fewer, bigger requests), and
the same one-open-not-two applies to the inline definition snippet. All client-side; the
local path is unchanged (framework defaults, serial early-exit). CODECOMPASS_FORCE_NETWORK
exercises every network-gated path on a local dir (tests, or a DFS/junction the root check
can't see).

Diagnostics for tuning these knobs from data, not guesswork:

- `codecompass survey <path>` reports what the caps currently skip (files with no
  go-to-definition, files absent from search), names the largest, and suggests a
  concrete config change - without changing anything.

- `codecompass symstats <path>` profiles, per language, the real file-size
  distribution (from stat only, so it is free even across millions of files) and
  whether the largest files actually yield symbols and how fast they parse. It is
  safe on a huge repo: it parses only the largest files per language, sequentially,
  each guarded by a timeout, so it can neither hang nor crawl.

- `codecompass parsebench` runs a synthetic parse-cost-vs-size sweep across content
  shapes, to characterize the curve on the local machine.

There is deliberately no auto-tuning of the caps. File size is not a reliable
signal of parse safety, and raising a cap is a judgement about a specific repo
that only its owner can make; the tools inform, the human decides.

Limitations, stated plainly. Documenting where the edges are is as important as
the features:

- Files over the file cap (default 2 GB) are absent from search entirely.
- Files over the symbol cap (default 1 MB), or classified as numeric data above
  1 MB when the cap is raised, or streamed (>=128 MB), have no go-to-definition
  (still text-searchable).
- Files >=128 MB are streamed (bounded memory) so they index up to the file cap.
  A search into one uses the per-file block/positional sidecar to read only the
  candidate ~1 MB blocks (network-friendly); UTF-8 only, else it falls back to a
  whole-file line scan.
- Text is indexed if it is UTF-8/ASCII or carries a UTF-16/UTF-32 byte-order mark
  (the decoders honor the BOM). A BOM-LESS UTF-16/32 file is indistinguishable from
  binary here - its ASCII bytes carry NULs with no marker - so it is treated as
  binary and skipped. Add a BOM (most Windows tools do) to have it indexed.
- `#define`/macro definitions are not captured as symbols by design; they are
  findable as text.
- The native tree-sitter parse cannot be cancelled through the binding, so slow
  parses are prevented by not starting them (size cap + content skip), never by
  interrupting them mid-parse.
- Precise C/C++ semantics need a compile database; without one, quality degrades
  to syntactic.
- Cross-process safety of deleting memory-mapped segment/base files while a reader
  holds them relies on Windows file-locking semantics.
- Linked roots: a link add/remove run in a terminal is picked up live (a signature
  check on links.json per query). A root linked while UNINDEXED (large, deferred to
  `codecompass index`) is federated once its index exists - immediately if the CLI
  built it inline, otherwise on the next reindex (the manual re-probe lever, since
  building it doesn't change links.json). A shared root edited by ANOTHER session's
  owner is refreshed in a read-only session only eventually (on that session's next
  reconcile/restart), not pushed live cross-process. A manual `codecompass index` on a
  root that already has a live owner is uncoordinated - the same as the project root's
  existing behavior.
- No embeddings / semantic-meaning search, and no multi-user server - both are
  out of scope for v1 by design, not by omission.


Open questions and risks
------------------------

- Real indexing throughput on a genuine dozens-of-GB polyglot repo on Windows
  hardware is unmeasured. This is the number that validates the whole premise
  and should be measured early, in phase 1.

- C/C++ semantic coverage depends on a compile database being present and
  correct. Where it isn't, quality drops to syntactic. We need to decide how
  hard to push on obtaining or generating compile_commands.json.

- The hard-block enforcement hook must be careful not to strand the agent when
  CodeCompass legitimately has no answer; the fallback path has to be reliable.

- Tree-sitter parse cost on pathological content was the biggest scaling risk and
  is now understood and handled - see "Scaling, huge files, and generated code"
  above. In short: parse is linear but with a ~70x content-dependent constant; the
  practical offenders are large machine-generated numeric data-blob files; the
  default symbol cap removes the hazard, and a fixed content check keeps it removed
  if the cap is raised. The earlier "roughly O(n^2)" framing in this document was
  wrong and has been corrected by measurement.

- Decided: build greenfield rather than adopt/fork an existing tool. We borrow
  designs (zoekt trigrams, Cursor Merkle diffing, tree-sitter) but own the code.
